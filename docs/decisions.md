## 決定の理由

### #1 上長の閲覧範囲：直属の部下のみ
最も単純で、権限の漏れが起きにくい。部署単位で閲覧したい要望が出たら、そのとき拡張する。

### #2 コメントへの返信：作らない
要件にあるのは「上長がコメントできる」ことだけ。返信が必要になったら、`COMMENT` に親コメントの ID を足せば対応できる。

### #3 訪問記録の追加項目：訪問時刻のみ
入力項目を増やすと日報を書く負担が増え、入力されなくなりやすい。運用しながら必要な項目を見極める。

### #4 提出後の編集：コメントが付くまで可
提出直後の誤字や追記は直せるようにする。上長がコメントした後に内容が変わると、コメントと本文が食い違うため編集できなくする。

### #5 顧客の担当：1人
今の要件の範囲では、担当営業は検索の絞り込みに使うだけ。複数担当が必要になったら、中間テーブルを追加する。

### #6 通知：作らない
上長は日報一覧の「●」（未コメント）で、コメントしていない日報が分かる。メールなどの通知は外部サービスとの連携が必要になるため、初期リリースには入れない。

### #7 管理者の日報閲覧：不可
管理者の役割はマスタ管理に限る。日報には顧客との商談内容が含まれるため、必要な人以外には見せない。

### #8 訪問記録0件での提出：提出できる（変更）
仮決めでは「不可」だったが、内勤日・会議の日・移動日など、訪問がない日も日報を出せないと運用できない。訪問がない日でも Problem と Plan を書くことには価値がある。Problem・Plan は引き続き必須とする。

### #9 過去日の作成：できる
出張や休み明けにまとめて書くことがあるため。未来日だけを禁止する。

### #10 部署：フリーテキスト
部署は検索と表示に使うだけで、部署ごとの権限はない。部署マスタを作るほどの必要はない。

### #11 スマートフォン入力：レスポンシブ対応のみ
画面定義書のとおり、スマートフォン幅では表をカード表示に切り替える。専用のレイアウトは利用状況を見てから検討する。

### #12 認証方式：セッションCookie（DB保存）
Next.js の公式ガイド（Authentication）が示す「データベースセッション」の方式に沿う。Cloud Run は複数インスタンスで動くため、セッションはメモリではなく DB に保存する。ブラウザ以外のクライアント（スマートフォンアプリ）の予定はないため、トークン方式は採らない。

### #13 下書きの削除：できる（変更）
仮決めでは「削除APIなし」だったが、報告日は作成後に変更できず、1人1日1件の制約がある。そのため、誤った日付で下書きを作ると、その日付の日報を作り直せなくなる。本人の下書きに限って削除できるようにする。提出済みの日報は削除できない。

### #14 コメント削除：物理削除
コメントは投稿者本人だけが削除でき、削除の履歴を残す要件はない。監査の要件が出たら論理削除に切り替える。

### #15 同時実行：行ロック
コメントが付いた日報の内容が後から書き換わることを防ぐ。日報の更新とコメントの投稿の両方で、日報の行をロックしてから処理する。

### #16 無効化された営業の過去の日報：閲覧できる
退職や異動の後も、過去の商談の経緯を上長が確認できる必要がある。`manager_id` は無効化しても残るため、実装上も自然に閲覧できる。

### #17 部下人数：無効な部下を含めない
部下人数は、上長を無効化するときの警告（M-11）に使う。無効な部下しかいない上長は無効化しても困らないため、数えない。

### #18 ログイン試行回数の制限：5回失敗で15分ロック（決定）
パスワードの総当たりを防ぐ。
- 同じメールアドレスへのログインに5回連続で失敗したら、そのメールアドレスでのログインを15分間受け付けない（正しいパスワードでも不可）
- 失敗回数はメールアドレスの文字列ごとに記録し、存在しないメールアドレスも同じように扱う（ロックされたかどうかで、アカウントの有無が分からないようにする）
- ログインに成功したら失敗回数をリセットする
- 15分たてば自動で解除される。管理者による解除の機能は作らない
- Cloud Run は複数インスタンスで動くため、失敗回数は DB に記録する

### #19 性能テストの前提規模：営業200人・5年分（変更）
仮決めは「営業200人・日報10万件」だったが、保存期間を考えると少なすぎるため見直した。
- 営業200人 × 年間約245営業日 × 5年 ＝ 日報約25万件
- 1日あたりの訪問を平均3件として、訪問記録約75万件
- データは最低5年間保持する

実際の営業の人数と異なる場合は、この数字を修正する。

## 実装時の決定

API の共通基盤（Issue #10）の実装時に、仕様書に書かれていなかった点を決めた（決定日：2026-11-01）。

### #20 409 の詳細コード：`reason` で返す（決定）
API 仕様書には「`409 CONFLICT`（`code` 詳細：`REPORT_LOCKED`）」とあり、詳細コードをどの項目で返すかが決まっていなかった。
- `code` に詳細コードを入れると、§1.5 の「409 は `CONFLICT`」という対応表が崩れ、画面側で `code` ごとの共通処理（例：409 なら再読み込みを促す）が書きにくくなる
- そのため `code` は HTTP ステータスと 1 対 1 のまま `CONFLICT` とし、理由を別の項目 `reason` で返す。テスト仕様書の「409 `REPORT_LOCKED`」は「`status=409` かつ `reason=REPORT_LOCKED`」と読む

### #21 単体のデータを返すレスポンス：`{ "data": ... }` で包む（決定）
A-03 は `{ "data": {...} }`、日報詳細（R-03）などは「日報オブジェクト」とだけ書かれていた。一覧（`{ data, meta }`）・エラー（`{ error }`）と形をそろえ、画面側の API クライアントで同じように扱えるよう、すべて `data` で包む。

### #22 ページングの範囲外の値：400 にする（決定）
`per_page` の上限（100）を超えた値を 100 に丸めると、指定した件数と違う結果が黙って返り、画面の不具合に気づきにくい。他の入力チェックと同じく `400 VALIDATION_ERROR` にする。

### #23 OpenAPI のサンプル API：ヘルスチェック API を追加する（決定）
OpenAPI 定義の生成（Issue #11）の確認に使うサンプル API が必要だった。仕様書の API はどれも認証（#16）や日報のスキーマ（#29）が前提で、まだ作れない。
- 開発用の仮の API を作って後で消すより、運用で使い続けられる API にする。Cloud Run の起動確認（#47）やデプロイ後の確認に使えるヘルスチェック API（H-01）を、仕様書に追加する
- 認証は不要とする。返すのは `status: "ok"` だけで、業務データは含まない
- `check=db` で DB への接続も確認できる。毎回 DB に接続すると起動確認のたびに接続を使うため、既定では確認しない

### #24 セッション Cookie の名前：`nipo_session`（決定）
OpenAPI の Cookie 認証（`securitySchemes`）に名前が必要なため、先に決めた。セッションの実装（#16）でも同じ定数（`SESSION_COOKIE_NAME`、`src/lib/api-constants.ts`）を使う。`__Host-` 接頭辞を付けるかは #16 で検討し、変える場合はこの定数と本記録を直す。

### #25 パスワードのハッシュ方式と最大文字数（決定）
パスワードの処理（Issue #13）の実装時に決めた。
- **ハッシュ方式は Argon2id**。OWASP Password Storage Cheat Sheet で第一に推奨されている方式。パラメーターも OWASP の推奨値（メモリ 19 MiB・反復 2 回・並列 1）にする。ライブラリは、Docker でのビルドにネイティブのコンパイルが要らない `@node-rs/argon2` を使う
- **最大 20 文字**。仕様書には最小（8 文字）しかなかった。非常に長いパスワードを送ってハッシュの計算に時間をかけさせる攻撃を防ぐため、上限を設ける。上限は PR #66 のレビューで 20 文字とした（当初案は 128 文字）。パスワード管理ツールで長いパスワードを使いたい要望が出たら見直す
- 存在しないユーザーのログインでも、ダミーのハッシュで同じ計算をしてから失敗にする。応答時間の差からアカウントの有無を推測させない（#18 の考え方に合わせる）
- パスワードポリシーは登録・変更のときだけ確認し、ログインでは確認しない。ポリシーを後から厳しくしても、既存のパスワードでログインできるようにするため
